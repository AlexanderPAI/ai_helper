# Календарь чатов и напоминания

## 1. Назначение документа

Этот документ описывает план добавления в Telegram-бот календаря с событиями и
напоминаниями. Он фиксирует целевую архитектуру, модель данных, компоненты,
инструменты агента, правила работы со временем и последовательность реализации.

Выбранный вариант: **PostgreSQL как постоянное хранилище и встроенный worker для
отправки напоминаний**.

Документ является планом. Он не описывает уже реализованную функциональность.

## 2. Цели

- У каждого Telegram-чата должен быть собственный календарь, определяемый по
  стабильному `chat_id`.
- Агент должен уметь создавать, просматривать, изменять и отменять события по
  просьбе пользователя на естественном языке.
- Для события можно назначить одно или несколько напоминаний.
- Каждое напоминание может иметь собственный текст, сформированный по инструкции
  пользователя и сохранённый вместе с напоминанием.
- Напоминания должны отправляться в тот же Telegram-чат в заданное время.
- События и напоминания должны сохраняться после перезапуска приложения,
  пересоздания контейнера и сброса контекста диалога.
- Доставка должна быть идемпотентной: один логический экземпляр напоминания не
  должен отправляться дважды.
- Ошибки Telegram и временные сбои должны приводить к повторным попыткам, а не к
  потере напоминания.

## 3. Границы первой версии

В первую версию входят:

- отдельный календарь для каждого `chat_id`;
- разовые события с обязательными названием, датой и временем;
- таймзона каждого чата;
- создание, получение, список, изменение и отмена событий;
- одно или несколько напоминаний для события;
- отдельный пользовательский текст для каждого напоминания;
- встроенный worker на основе периодического опроса PostgreSQL;
- повторные попытки при временных ошибках отправки;
- понятное подтверждение каждого изменения пользователю;
- сохранение автора создания и основных временных меток для аудита.

Не входят в первую версию:

- синхронизация с Google Calendar, Outlook и другими внешними календарями;
- повторяющиеся события;
- отдельные личные календари участников внутри группового чата;
- веб-интерфейс календаря;
- Redis, Celery или отдельный брокер задач;
- вложения и приглашения внешних участников.

Повторяющиеся события можно добавить отдельным этапом после стабилизации
разовых событий. Для них потребуется аккуратная работа с правилами повторения,
таймзонами и переходами на летнее время.

## 4. Ключевые архитектурные решения

### 4.1. Календарь привязан к `chat_id`

`chat_id` — стабильный идентификатор владельца календаря. UUID-сессия LangGraph
используется только для истории диалога и не участвует в идентификации календаря.

```text
chat_id    -> настройки календаря, события и напоминания
session_id -> история текущего диалога LangGraph
```

Команда `/reset` должна:

1. удалить checkpoints текущей UUID-сессии;
2. создать новую UUID-сессию для чата;
3. не изменять таблицы календаря;
4. не отменять события и напоминания.

После сброса агент не помнит прежнее обсуждение, но может заново получить
актуальные события через инструменты календаря.

### 4.2. PostgreSQL — единственный источник истины

Все события, настройки и состояния доставки хранятся в PostgreSQL. Worker не
держит критичное состояние только в памяти и не полагается на долгоживущие
`asyncio.sleep()` до момента события.

После перезапуска worker продолжает обработку на основании записей в БД.

### 4.3. Запись события и доставка напоминания разделены

Агент управляет календарными данными через прикладной сервис и репозиторий.
Worker независимо выбирает наступившие напоминания и отправляет их через Telegram.

Это позволяет:

- не связывать доставку с активным запросом пользователя;
- восстанавливать работу после перезапуска;
- повторять временно неуспешные отправки;
- позднее вынести worker в отдельный процесс без переделки модели данных.

### 4.4. `chat_id` нельзя доверять модели

Модель не должна передавать `chat_id` аргументом инструмента. Настоящий `chat_id`
известен Telegram-слою и должен попадать в календарный инструмент через доверенный
runtime-контекст вызова.

Иначе модель теоретически может ошибиться, использовать идентификатор из текста
или обратиться к календарю другого чата.

## 5. Общая схема компонентов

```text
Telegram message
      |
      v
TelegramAgentBot -- trusted chat_id/user_id --> Agent runtime context
      |                                           |
      |                                           v
      |                                    Calendar tools
      |                                           |
      |                                           v
      |                                    Calendar service
      |                                           |
      |                                           v
      |                                   Calendar repository
      |                                           |
      |                                           v
      |                                      PostgreSQL
      |
      |             Reminder worker <-------------+
      |                    |
      +<---- Telegram Bot API
```

Планируемые компоненты:

1. Модели предметной области календаря.
2. Репозиторий PostgreSQL.
3. Прикладной сервис календаря.
4. Инструменты агента.
5. Доверенный контекст вызова инструмента.
6. Встроенный worker напоминаний.
7. Конфигурация БД, worker и временных зон.
8. Миграции схемы.
9. Тесты всех уровней.

## 6. Модель данных

Ниже приведена логическая модель. Конкретные типы и названия могут уточняться во
время реализации миграций.

### 6.1. `calendar_chats`

Хранит настройки календаря конкретного Telegram-чата.

| Поле | Тип | Назначение |
|---|---|---|
| `chat_id` | `BIGINT`, PK | Telegram ID чата и владелец календаря |
| `timezone` | `TEXT` | IANA-таймзона, например `Europe/Moscow` |
| `created_at` | `TIMESTAMPTZ` | Дата создания настроек |
| `updated_at` | `TIMESTAMPTZ` | Дата последнего изменения |

Настройки могут создаваться лениво при первом календарном действии в чате.
На первом этапе таблица хранит только настройки, которые действительно относятся
ко всему календарю чата. В ней нет времени напоминания по умолчанию: момент и
текст каждого напоминания задаются в контексте конкретного события.

### 6.2. `calendar_events`

| Поле | Тип | Назначение |
|---|---|---|
| `id` | `UUID`, PK | Внутренний ID события |
| `chat_id` | `BIGINT`, FK | Владелец события |
| `title` | `TEXT` | Краткое название |
| `description` | `TEXT`, nullable | Дополнительное описание |
| `starts_at` | `TIMESTAMPTZ` | Момент начала в UTC |
| `source_timezone` | `TEXT` | Таймзона, в которой пользователь задал время |
| `status` | enum/text | `active`, `cancelled`, `completed` |
| `created_by_user_id` | `BIGINT`, nullable | Telegram ID автора |
| `created_by_display_name` | `TEXT`, nullable | Снимок имени автора для отображения |
| `created_at` | `TIMESTAMPTZ` | Дата создания |
| `updated_at` | `TIMESTAMPTZ` | Дата изменения |
| `cancelled_at` | `TIMESTAMPTZ`, nullable | Дата отмены |
| `version` | `INTEGER` | Версия для защиты от конкурирующих изменений |

Событие не удаляется физически обычной пользовательской операцией. Отмена через
статус сохраняет аудит и не позволяет worker отправить ещё не наступившие
напоминания.

Основные индексы:

- `(chat_id, starts_at)` для списка событий чата;
- `(chat_id, status, starts_at)` для ближайших активных событий;
- индекс по `updated_at` при необходимости аудита и диагностики.

### 6.3. `event_reminders`

| Поле | Тип | Назначение |
|---|---|---|
| `id` | `UUID`, PK | ID логического напоминания |
| `event_id` | `UUID`, FK | Связанное событие |
| `remind_at` | `TIMESTAMPTZ` | Плановое время доставки в UTC |
| `message_text` | `TEXT` | Текст, который worker отправит в напоминании |
| `status` | enum/text | `pending`, `processing`, `sent`, `failed`, `cancelled` |
| `attempts` | `INTEGER` | Количество начатых попыток |
| `next_attempt_at` | `TIMESTAMPTZ` | Когда разрешена следующая попытка |
| `locked_at` | `TIMESTAMPTZ`, nullable | Время резервирования worker-ом |
| `locked_by` | `TEXT`, nullable | ID экземпляра worker-а |
| `sent_at` | `TIMESTAMPTZ`, nullable | Фактическое время успешной доставки |
| `telegram_message_id` | `BIGINT`, nullable | ID отправленного сообщения |
| `last_error` | `TEXT`, nullable | Последняя ошибка доставки |
| `created_at` | `TIMESTAMPTZ` | Дата создания |
| `updated_at` | `TIMESTAMPTZ` | Дата изменения |

Ограничения и индексы:

- уникальность `(event_id, remind_at)`, чтобы не создать одинаковое напоминание
  дважды;
- индекс `(status, next_attempt_at)` для worker-а;
- внешняя ссылка на событие;
- непустой `message_text` с ограничением длины на уровне сервиса;
- проверка, что `attempts >= 0`.

Если время события изменилось, связанные неотправленные напоминания должны быть
пересчитаны в одной транзакции. Уже отправленные напоминания остаются частью
истории.

### 6.4. Возможный журнал действий

Таблица `calendar_event_audit` не обязательна для MVP. Она может понадобиться,
если потребуется полная история изменений: кто, когда и какие поля поменял.

На первом этапе достаточно метаданных события, мягкой отмены и логов приложения.

## 7. Слой репозитория

Инструменты агента и worker не должны выполнять SQL напрямую. Репозиторий
инкапсулирует запросы и транзакции.

Планируемые операции репозитория:

- получить или создать настройки календаря чата;
- изменить таймзону и настройки по умолчанию;
- создать событие вместе с напоминаниями в одной транзакции;
- получить событие строго в границах заданного `chat_id`;
- получить ближайшие события чата;
- найти кандидатов по названию и временному диапазону;
- изменить событие и пересчитать его будущие напоминания;
- отменить событие и его неотправленные напоминания;
- атомарно зарезервировать пачку наступивших напоминаний;
- отметить напоминание отправленным;
- запланировать повторную попытку;
- пометить напоминание окончательно неуспешным;
- вернуть зависшие `processing`-напоминания в очередь после истечения lease.

Каждая операция чтения или изменения пользовательского события должна включать
условие по `chat_id`. Одного `event_id` недостаточно: это важная граница изоляции
календарей.

## 8. Прикладной сервис календаря

Между инструментами и репозиторием нужен сервис с бизнес-правилами. Он отвечает
за:

- проверку названия и длины описания;
- проверку и нормализацию текста каждого напоминания;
- преобразование локального времени в UTC;
- запрет создания события в недопустимо далёком прошлом;
- проверку времени напоминаний;
- защиту от дубликатов;
- пересчёт напоминаний при переносе события;
- формирование структурированного результата для ответа пользователю;
- проверку статуса и версии события при изменении.

Так бизнес-логика остаётся одинаковой независимо от того, вызвана она агентом,
будущей командой бота или административным интерфейсом.

## 9. Инструменты агента

### 9.1. `create_calendar_event`

Назначение: создать событие и напоминания.

Аргументы модели:

- `title`;
- `description`, опционально;
- локальные дата и время либо однозначное ISO-представление;
- таймзона, только если пользователь указал её явно;
- список напоминаний, каждое из которых содержит смещение или точное время и
  собственный `message_text`;
- необязательный ключ идемпотентности, если механизм формируется приложением.

Не принимает `chat_id` и `created_by_user_id`: они добавляются приложением из
доверенного контекста.

Пример пользовательского намерения:

```text
Сохрани встречу на 12 августа в 15:00. Напомни за час и обязательно упомяни,
что нужно взять договор и позвонить Анне.
```

Инструмент должен получить напоминание примерно в таком структурированном виде:

```json
{
  "offset_minutes": 60,
  "message_text": "Возьми договор и позвони Анне перед встречей."
}
```

Модель преобразует явную инструкцию пользователя в готовый текст, а сервис
сохраняет этот текст без смыслового переосмысления. Worker позднее берёт его из
БД; для отправки напоминания повторный вызов LLM не требуется.

### 9.2. `list_calendar_events`

Назначение: показать события текущего чата.

Аргументы:

- начало и конец периода;
- максимальное количество;
- при необходимости фильтр по статусу или тексту.

По умолчанию возвращает ближайшие активные события, а не всю историю.

### 9.3. `get_calendar_event`

Назначение: получить точные детали одного события перед изменением или отменой.

Аргументы:

- `event_id`.

Получение всегда ограничено текущим `chat_id` на серверной стороне.

### 9.4. `update_calendar_event`

Назначение: изменить название, описание, время, расписание напоминаний или их
тексты.

Аргументы:

- `event_id`;
- только изменяемые поля;
- при изменении напоминаний — их время и итоговый `message_text`;
- опционально ожидаемая `version` для защиты от устаревшего изменения.

При изменении даты или времени сервис пересчитывает будущие напоминания в одной
транзакции.

### 9.5. `delete_calendar_event`

Пользовательское название инструмента можно оставить привычным, но фактически он
выполняет мягкую отмену.

Аргументы:

- `event_id`;
- опциональная причина отмены.

Все `pending` и `processing` напоминания события отменяются.

### 9.6. Возможные дополнительные инструменты

После MVP:

- `set_chat_timezone`;
- `get_chat_calendar_settings`;
- `restore_calendar_event`;
- отдельный `set_event_reminders`, если обновление события станет слишком
  перегруженным;
- инструменты повторяющихся событий.

## 10. Доверенный контекст вызова

Текущий контракт инструмента принимает только аргументы LLM. Его потребуется
расширить так, чтобы при вызове инструмента были доступны данные запроса:

- `chat_id`;
- `user_id`;
- отображаемое имя пользователя;
- ID исходного Telegram-сообщения;
- текущая дата и время приложения;
- таймзона чата после загрузки настроек.

Контекст создаётся в Telegram-слое и передаётся в агент отдельно от текста
пользователя. Поля безопасности нельзя переопределить аргументами модели.

Все инструменты календаря работают только с календарём `context.chat_id`.

## 11. Планировщик и worker напоминаний

### 11.1. Размещение

В первой версии worker запускается как фоновая coroutine внутри процесса бота.
Он использует тот же пул подключений PostgreSQL и тот же объект Telegram Bot.

Архитектурно worker должен быть самостоятельным классом без зависимости от
обработчика входящих сообщений. Это позволит позднее запустить его отдельным
Docker-сервисом без изменения бизнес-логики.

### 11.2. Цикл работы

1. Worker с заданным интервалом запрашивает небольшую пачку напоминаний, для
   которых `status = pending` и `next_attempt_at <= now()`.
2. В короткой транзакции записи блокируются через `FOR UPDATE SKIP LOCKED`.
3. Выбранные записи переводятся в `processing`, им назначаются `locked_at`,
   `locked_by`, увеличивается `attempts`.
4. Транзакция завершается до сетевого вызова Telegram.
5. Worker отправляет каждое сообщение.
6. После успеха запись переводится в `sent`, сохраняются `sent_at` и ID сообщения.
7. После временной ошибки запись возвращается в `pending`, а
   `next_attempt_at` переносится согласно политике повторов.
8. После постоянной ошибки или исчерпания попыток запись переводится в `failed`.

Сетевой вызов нельзя выполнять, удерживая блокировку транзакции PostgreSQL.

### 11.3. Защита от зависших заданий

Если процесс завершился после перевода записи в `processing`, она может остаться
заблокированной логически. Worker должен периодически возвращать в очередь
записи, у которых lease истёк:

```text
status = processing AND locked_at < now() - processing_timeout
```

### 11.4. Повторные попытки

Предварительная политика:

- короткая задержка после первой ошибки;
- экспоненциальное увеличение задержки с верхним пределом;
- ограниченное число попыток;
- добавление небольшого случайного jitter;
- сохранение краткого текста последней ошибки.

Ошибки делятся на:

- временные: timeout, сетевой сбой, ограничение частоты, временная ошибка Telegram;
- постоянные: чат недоступен, бот заблокирован, некорректный получатель;
- неизвестные: повторяются ограниченное число раз, затем переводятся в `failed`.

### 11.5. Идемпотентность и граница гарантий

PostgreSQL предотвращает параллельную обработку одной записи несколькими
worker-ами. Однако между успешным ответом Telegram и записью `sent` возможен сбой
процесса. Telegram Bot API не предоставляет полноценного идемпотентного ключа для
обычной отправки сообщений, поэтому абсолютная гарантия exactly-once недостижима.

Целевая гарантия — **at-least-once с максимальным снижением вероятности дубля**:

- короткий участок между отправкой и фиксацией результата;
- уникальная запись логического напоминания;
- lease и контролируемые повторы;
- сохранение Telegram message ID после успеха;
- наблюдаемость повторной обработки.

При необходимости позже можно добавить защитный маркер доставки или более
осторожную ручную обработку неопределённого результата.

### 11.6. Остановка приложения

При graceful shutdown приложение должно:

1. прекратить получение новых пачек;
2. дать выполняющимся отправкам ограниченное время завершиться;
3. закрыть worker;
4. затем закрыть Telegram-клиент и пул БД.

Незавершённые `processing`-записи будут восстановлены по истечении lease.

## 12. Работа с датой, временем и таймзонами

### 12.1. Правила хранения

- Абсолютные моменты хранятся в PostgreSQL как `TIMESTAMPTZ` в UTC.
- Таймзона чата хранится отдельно в формате IANA, например `Europe/Moscow`.
- У события сохраняется `source_timezone`, чтобы корректно отображать исходное
  намерение пользователя и в будущем поддержать повторения.
- Форматирование ответа выполняется в таймзоне чата или в явно указанной
  таймзоне события.

Нельзя хранить пользовательское время только как наивные дату и часы без
таймзоны.

### 12.2. Получение таймзоны

Порядок выбора:

1. явно указанная пользователем таймзона;
2. сохранённая таймзона чата;
3. настроенная системная таймзона по умолчанию;
4. уточнение у пользователя, если безопасного значения по умолчанию нет.

Для текущего проекта допустимо начать с `Europe/Moscow` как конфигурируемого
значения по умолчанию, но в подтверждении всегда показывать таймзону.

### 12.3. Относительные выражения

Выражения «завтра», «в пятницу», «через два часа» интерпретируются относительно:

- текущего времени приложения;
- таймзоны текущего чата;
- даты получения исходного сообщения.

Модель может предложить структурированную дату инструменту, но сервис обязан
проверить её допустимость. В runtime-контекст нужно передавать точное текущее
время, чтобы модель не угадывала дату.

### 12.4. Неоднозначные значения

Агент не должен создавать событие, если существенно неоднозначны:

- дата;
- время;
- таймзона;
- выбранное событие для изменения или удаления.

Примеры, требующие уточнения:

- «Запиши встречу в пятницу» без времени, если время по умолчанию не задано;
- «Напомни в 8» без возможности понять утро или вечер;
- «Перенеси созвон на час» при нескольких созвонах;
- дата, которая после разбора оказалась в прошлом.

### 12.5. Напоминания относительно события

Пользователь задаёт напоминание как смещение, например `15 минут до события`.
Сервис преобразует его в абсолютный `remind_at`.

Правила:

- `remind_at` должен быть раньше `starts_at` либо равен ему для напоминания «в
  момент события»;
- нельзя молча создавать уже просроченное напоминание;
- при переносе события будущие напоминания пересчитываются;
- уже отправленные напоминания не отправляются повторно автоматически;
- если пользователь не попросил о напоминании, событие создаётся без него;
- если пользователь попросил напомнить, но не назвал момент, агент должен
  уточнить, когда отправить напоминание;
- каждое создаваемое напоминание должно иметь непустой итоговый текст;
- если пользователь явно перечислил сведения, которые нужно упомянуть, итоговый
  текст обязан содержать все эти сведения;
- если пользователь указал время напоминания, но не задал особый текст, агент
  формирует нейтральный текст из названия и доступного описания события;
- текст фиксируется в БД в момент создания или изменения и не генерируется
  worker-ом во время доставки.

### 12.6. Пользовательский текст напоминания

Текст напоминания является самостоятельным свойством напоминания, а не события.
Это позволяет одному событию иметь несколько уведомлений с разными сообщениями,
например:

- за день: «Подготовь документы и согласуй повестку с Анной»;
- за 15 минут: «Подключайся к созвону, ссылка лежит в описании».

Правила формирования текста:

1. Агент извлекает из запроса все обязательные упоминания пользователя.
2. Формирует короткий готовый текст без добавления новых фактов.
3. Передаёт итоговый текст аргументом календарного инструмента.
4. Сервис валидирует, что текст непустой и помещается в установленный лимит.
5. Текст сохраняется в `event_reminders.message_text`.
6. Подтверждение создания показывает пользователю точный сохранённый текст.
7. Worker отправляет именно сохранённый текст, не обращаясь к истории диалога и
   не вызывая LLM.

Если обязательные сведения противоречат друг другу или неясно, к какому из
нескольких напоминаний они относятся, агент сначала задаёт уточняющий вопрос.

## 13. Поиск события для изменения и удаления

Пользователь редко знает UUID события. Поэтому нужен двухшаговый сценарий:

1. агент получает список кандидатов текущего чата по названию и временному
   диапазону;
2. если найден ровно один очевидный кандидат, используется его `event_id`;
3. если кандидатов несколько, бот показывает краткий список и просит выбрать;
4. после выбора выполняется изменение или отмена.

Нельзя поручать репозиторию «удалить первое событие с похожим названием».

Внутренний ID можно включать в структурированный результат инструмента и историю
агента, но в пользовательском сообщении достаточно короткого ID или даты.

## 14. Подтверждение действий пользователю

После успешного изменения агент должен показать результат в нормализованном виде,
полученном от сервиса, а не заново пересобирать факты из исходного запроса.

Пример создания:

```text
Создал событие «Созвон с командой».
12 августа 2026 года, 15:00 МСК.
Напомню за 30 минут.
Текст напоминания: «Возьми договор и позвони Анне».
```

Пример переноса:

```text
Перенёс «Созвон с командой» на 13 августа, 16:00 МСК.
Напоминание за 30 минут также перенесено.
```

Пример отмены:

```text
Отменил событие «Созвон с командой» на 13 августа, 16:00 МСК.
Будущие напоминания отправлены не будут.
```

Подтверждение должно всегда содержать:

- выполненное действие;
- название события;
- полную дату;
- время и понятное обозначение таймзоны;
- время и точный сохранённый текст каждого напоминания;
- предупреждение, если часть действия выполнить не удалось.

Инструмент возвращает структурированный результат, включающий ID и фактически
сохранённые значения. Финальный текст строится только по этому результату.

## 15. Формат сообщения напоминания

Worker использует стабильную служебную обёртку, а пользовательская часть берётся
из `event_reminders.message_text` без повторной генерации:

```text
⏰ Напоминание

Созвон с командой
Сегодня в 15:00 МСК

Возьми договор и позвони Анне.
```

Заголовок, название и время формируются детерминированно из события. Кастомный
текст выводится отдельным абзацем дословно в сохранённой редакции. Сообщение не
должно требовать наличия активной сессии LangGraph и отправляется worker-ом
напрямую.

## 16. Транзакции и конкурентный доступ

Транзакция обязательна для следующих операций:

- создание события вместе со всеми напоминаниями;
- изменение времени и пересчёт напоминаний;
- отмена события и отмена его напоминаний;
- резервирование пачки worker-ом;
- фиксация результата попытки доставки.

В одном групповом чате запросы сейчас сериализуются lock-ом процесса, но на это
нельзя полагаться как на гарантию данных: после масштабирования будет несколько
процессов. Целостность обеспечивают PostgreSQL, ограничения схемы, транзакции и
поле `version`.

## 17. Конфигурация

Потребуются настройки примерно следующих групп:

### PostgreSQL

- DSN подключения;
- размер пула;
- timeout подключения и запросов;
- параметры SSL для production.

### Worker

- включён ли worker в текущем процессе;
- интервал опроса;
- размер пачки;
- processing timeout/lease;
- максимальное количество попыток;
- начальная и максимальная задержка повторов;
- уникальный ID экземпляра worker-а.

### Календарь

- таймзона по умолчанию;
- максимально допустимый горизонт события;
- лимит событий в выдаче;
- допустимые длины названия, описания и текста напоминания.

Секреты и DSN задаются через `.env`, а безопасные значения по умолчанию — через
настройки приложения.

## 18. Docker и эксплуатация

В `docker-compose` планируется добавить:

- сервис PostgreSQL;
- именованный volume для каталога данных PostgreSQL;
- healthcheck БД;
- зависимость запуска бота от готовности БД;
- переменные подключения.

Контейнер бота остаётся без локального постоянного состояния. Удаление или
пересоздание контейнера бота не затрагивает календарь.

Для production потребуются:

- регулярные резервные копии PostgreSQL;
- проверка восстановления из копии;
- ограниченный пользователь БД;
- мониторинг свободного места;
- применение миграций перед запуском новой версии.

## 19. Миграции

Схема должна управляться миграциями, например Alembic.

Требования:

- первая миграция создаёт настройки чатов, события и напоминания;
- миграции хранятся в репозитории;
- обновление схемы выполняется явным шагом deployment-а;
- приложение не создаёт таблицы неявно при каждом запуске;
- изменения enum-статусов и индексов также оформляются миграциями.

## 20. Обработка ошибок

### Ошибки пользовательского ввода

Возвращаются агенту как понятный структурированный результат: что именно нужно
уточнить или исправить. Они не должны выглядеть как внутренний сбой приложения.

### Ошибки БД

- транзакция откатывается;
- пользователю не подтверждается несохранённое действие;
- техническая причина пишется в лог;
- наружу возвращается нейтральное сообщение о временной недоступности календаря.

### Ошибки worker-а

- ошибка одной отправки не останавливает цикл;
- состояние и следующая попытка сохраняются в БД;
- неожиданные ошибки логируются с `event_id`, `reminder_id` и `chat_id`;
- секреты и полное содержимое приватных сообщений в лог не попадают.

## 21. Наблюдаемость

В структурированные логи стоит включать:

- создание, изменение и отмену события;
- `chat_id`, `event_id`, `reminder_id`;
- резервирование пачки worker-ом;
- успешную доставку и длительность;
- номер попытки и категорию ошибки;
- восстановление зависшего задания;
- размер backlog готовых напоминаний.

Полезные метрики на будущее:

- количество `pending`, `processing` и `failed` напоминаний;
- задержка между `remind_at` и `sent_at`;
- доля успешных отправок с первой попытки;
- число восстановленных lease;
- количество календарных действий по типам.

## 22. Безопасность и изоляция

- `chat_id` и `user_id` поступают только из Telegram update.
- Модель не выбирает календарь, с которым работает.
- Каждая операция с событием проверяет принадлежность текущему `chat_id`.
- В SQL используются параметризованные запросы или ORM.
- Тексты ошибок БД и Telegram не показываются пользователю напрямую.
- Длина и формат полей события ограничены.
- Календарные инструменты доступны только уже разрешённым чатам.
- В логах не сохраняются токены, DSN с паролем и другие секреты.

## 23. Тестирование

### Модульные тесты

- преобразование локального времени в UTC и обратно;
- относительные даты вокруг полуночи;
- валидация напоминаний;
- сохранение и валидация пользовательского текста напоминания;
- сохранение всех явно запрошенных обязательных упоминаний;
- пересчёт напоминаний при переносе;
- форматирование подтверждений и сообщений worker-а;
- классификация ошибок доставки и backoff.

### Тесты репозитория с PostgreSQL

- изоляция данных разных `chat_id`;
- атомарное создание события и напоминаний;
- уникальность напоминаний;
- конкурентное резервирование через `SKIP LOCKED`;
- восстановление истёкшего lease;
- отмена события вместе с будущими напоминаниями;
- optimistic locking через `version`.

### Интеграционные тесты агента

- модель вызывает правильный инструмент;
- доверенный `chat_id` не берётся из аргументов модели;
- неоднозначный запрос приводит к уточнению;
- инструкция «в напоминании обязательно упомяни ...» полностью попадает в
  `message_text`;
- список и изменение работают только внутри текущего чата;
- результат инструмента корректно превращается в подтверждение.

### Интеграционные тесты worker-а

- наступившее напоминание отправляется и становится `sent`;
- worker отправляет сохранённый `message_text` без вызова LLM;
- будущее напоминание не отправляется;
- временная ошибка создаёт повторную попытку;
- постоянная ошибка переводит запись в `failed`;
- перезапуск восстанавливает зависшее `processing`-напоминание;
- отменённое событие не отправляется.

### Сквозные сценарии

1. Создать событие в чате A.
2. Убедиться, что чат B его не видит.
3. Выполнить `/reset` в чате A.
4. Убедиться, что событие всё ещё доступно.
5. Дождаться напоминания.
6. Перезапустить бот до времени другого напоминания и проверить доставку после
   запуска.

## 24. Этапы реализации

### Текущее состояние

- Этап 1 завершён: добавлены PostgreSQL, SQLAlchemy 2.0, asyncpg, Alembic,
  начальная миграция и отдельная тестовая БД.
- Этап 2 завершён: пакет `calendar_app` содержит независимые доменные модели,
  PostgreSQL-репозиторий и транзакционный `CalendarService`.
- Интеграция сервиса с агентом, Telegram и worker-ом ещё не выполнена.

Публичные операции реализованного сервиса:

- получить и изменить таймзону календаря чата;
- создать событие с произвольными текстами напоминаний;
- получить событие строго в пределах `chat_id`;
- получить отфильтрованный список событий;
- изменить событие с optimistic locking по `version`;
- перенести событие с сохранением смещений и текстов будущих напоминаний;
- заменить расписание или текст напоминаний;
- мягко отменить событие и все открытые напоминания.

Все изменяющие операции сервиса выполняются в транзакциях. Локальные даты
проверяются через IANA-таймзоны и сохраняются в UTC; несуществующее и неоднозначное
локальное время отклоняется.

### Этап 1. Инфраструктура хранения

- выбрать библиотеку работы с PostgreSQL;
- добавить настройки подключения;
- добавить PostgreSQL и volume в Docker Compose;
- настроить миграции;
- создать первую схему таблиц и индексов;
- добавить тестовую PostgreSQL-среду.

Результат: приложение может надёжно подключаться к версионируемой схеме БД.

### Этап 2. Домен, репозиторий и сервис

- определить доменные модели и статусы;
- реализовать CRUD репозитория;
- реализовать транзакционные операции;
- добавить бизнес-правила времени и напоминаний;
- покрыть слой тестами.

Результат: календарём можно полностью управлять без участия LLM и Telegram.

### Этап 3. Runtime-контекст и инструменты агента

- передавать доверенные Telegram-метаданные в вызов агента;
- добавить инструменты создания, списка, получения, изменения и отмены;
- обновить системный промпт с правилами уточнения;
- добавить структурированные результаты инструментов;

Результат: пользователь управляет календарём естественным языком, а календари
чатов изолированы.

Результат: функцию можно безопасно эксплуатировать на VPS.

## 25. Критерии готовности MVP

MVP считается готовым, когда выполняются все условия:

- два разных `chat_id` не могут получить доступ к событиям друг друга;
- `/reset` не удаляет и не изменяет календарные данные;
- событие сохраняется после перезапуска бота;
- пользователь может создать, просмотреть, изменить и отменить событие;
- неоднозначные дата и выбранное событие приводят к уточнению;
- все подтверждения содержат полную дату, время и таймзону;
- напоминание отправляется после перезапуска приложения;
- временная ошибка Telegram приводит к повторной попытке;
- отменённое событие больше не порождает напоминания;
- параллельные worker-ы не резервируют одну запись одновременно;
- есть миграции, автоматические тесты и инструкция резервного копирования.

## 26. Решения, которые нужно принять перед реализацией

Перед началом разработки нужно окончательно выбрать:

1. Библиотеку доступа к PostgreSQL и способ описания моделей.
2. Инструмент миграций.
3. Таймзону по умолчанию.
4. Максимальную длину пользовательского текста напоминания.
5. Максимальное количество напоминаний на одно событие.
6. Политику для напоминания, время которого уже прошло.
7. Интервал worker-а, размер пачки, lease и число повторных попыток.
8. Нужна ли команда настройки календаря уже в MVP.
9. Требуется ли подтверждение перед отменой однозначно найденного события.
10. Как показывать пользователю несколько совпавших событий: текстом или
    Telegram-кнопками.

Рекомендуемые стартовые решения:

- асинхронный PostgreSQL-драйвер и пул подключений;
- Alembic для миграций;
- `Europe/Moscow` как конфигурируемая таймзона по умолчанию;
- события без напоминаний разрешены, а момент напоминания не назначается молча;
- пользовательский текст напоминания хранится отдельно для каждого уведомления;
- до пяти напоминаний на событие;
- polling каждые 10 секунд небольшими пачками;
- мягкая отмена события;
- текстовое уточнение при нескольких кандидатах;
- worker внутри процесса, но с интерфейсом, пригодным для последующего выделения.
